# Insolvency data hub - architecture and conventions

Plain-English note: this file explains how the behind-the-scenes data for the
insolvency data pages is organised, and how to refresh it each month. It is the
internal reference. The public-facing version of this becomes the methodology
page (Phase 8).

## What this hub is

A data product, not advice content. Official statistics, source-backed tables,
repeatable monthly charts, and pages a journalist, accountant or lender can cite.
Guidance ("what is insolvency", "what should directors do") lives on the existing
advice pages and is only linked to, never rewritten here.

## Source hierarchy

Defined in `data/_meta/source_registry.json`. Authority runs highest to lowest:

1. **Insolvency Service** (`insolvency_service_monthly`) - official statistical
   backbone. Implemented.
2. **Companies House** (`companies_house_register`) - company population,
   incorporations and dissolutions; denominator and identity data. Planned.
3. **The Gazette** (`the_gazette_notices`) - winding-up petitions and other legal
   notices; the early-warning layer. Planned.
4. **ONS** (`ons_business`) - business population, sector context, denominators.
   Planned.
5. **Payment practices** (`payment_practices`) - late-payment enrichment only.
   Planned.

Rule: no single source gives a complete real-time distress timeline. Pages build
a multi-source picture with an explicit source, date type and caveats - they do
not silently blend sources.

## Data files (V1 = tidy JSON, no database)

| File | Purpose |
|---|---|
| `data/_meta/source_registry.json` | Every upstream source, with licence and authority level. |
| `data/_meta/caveats.json` | Reusable caveat wording, referenced by id so disclaimers stay consistent. |
| `data/<dataset>/dataset_release.json` | Release ledger - one entry per monthly release, with file hashes. Superseded releases are kept, never deleted. |
| `data/<dataset>/*.json` | The parsed series the charts and tables read (e.g. `monthly_series.json`). |

`scripts/datahub/registry.py` loads and validates all of the above. Run
`python scripts/datahub/registry.py` for a self-check; it fails if a release
cites an unregistered source or a required field is missing.

The brief's `stat_observation` and `company_event` shapes are the target for
when ONS denominators and Gazette events arrive. Until then the per-page series
JSON stands in for `stat_observation`, and `company_event` is deferred.

## Source fetchers (implemented)

Each command fetches the latest data, stores it under `data/<dataset>/`, and
writes a release into that dataset's `dataset_release.json`.

| Source | Command | Key needed |
|---|---|---|
| Insolvency Service | drop monthly files, then `python scripts/parse_insolvency_data.py` | none |
| Companies House | `python scripts/datahub/sources/companies_house.py --month YYYY-MM` | `COMPANIES_HOUSE_API_KEY` in `.env` |
| The Gazette | `python scripts/datahub/sources/the_gazette.py --month YYYY-MM` | none (public feed) |
| ONS business counts | `python scripts/datahub/sources/ons_business.py` | none (Nomis) |

After any fetch, run `python scripts/datahub/registry.py` to confirm the
backbone is consistent. Payment practices (enrichment only) is not yet built.

## Monthly update workflow (Insolvency Service)

1. Drop the new CSV + XLSX into `data/insolvency-statistics/`.
2. Run `python scripts/parse_insolvency_data.py`.
3. Run `python scripts/build_insolvency_charts.py` (and the dashboard builder).
4. Add a new entry to `dataset_release.json`; set the previous entry's `status`
   to `superseded` (do not delete it). Record file hashes.
5. Check the headline values against the source release.
6. Check the chart outputs render.
7. Update the source / citation and "last updated / next release" labels.
8. Note any revisions in the release `notes`.
9. Run `python scripts/datahub/registry.py` to confirm the backbone is consistent.

## Protecting generated drafts (CD-NO-AUTOEDIT)

Data-hub page drafts are generated by a builder (e.g.
`build_insolvency_dashboard.py`) and contain large inline SVG. The article
pipelines (internal-link injection, Bernstein `wp_post` rewrite) must never
auto-edit them - doing so corrupts the markup and replaces the dashboard with
prose. This happened once: the committed draft for post 77399 was overwritten
by an internal-links / rewrite batch.

Guard: every generated draft carries a sentinel comment near the top:

    <!-- CD-NO-AUTOEDIT: data_reference page generated by ... -->

- `scripts/add_internal_links.py` skips any draft containing `CD-NO-AUTOEDIT`
  (it is excluded from the draft index, so it is neither read nor written).
- TODO: apply the same skip in the Bernstein `wp_post` rewrite path
  (`editorial-os/`) and any future bulk draft writer. Until then, do not run a
  full `wp_post` rewrite batch over data_reference slugs.

## Freshness labels

`Latest`, `Provisional`, `Revised`, `Archived`, `Methodology changed`. These map
to the `status` and `is_provisional` fields in `dataset_release.json`.

## Caveats

Centralised in `data/_meta/caveats.json`. Pages cite by id rather than re-wording.
Key ones: `latest_provisional`, `sa_vs_nsa`, `nations_sa_difference`,
`sector_lag`, `sic_self_reported`, `registered_office`,
`sector_volumes_not_rates`, `gazette_not_outcome`,
`dissolutions_not_insolvencies`, `ons_denominator`.
